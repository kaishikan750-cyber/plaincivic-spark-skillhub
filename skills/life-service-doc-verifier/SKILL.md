# 生活办事材料核验管家

## 用途

将用户提供的当前办事通知编译为带条件和来源的核验清单，再与用户现有材料逐项比对。目标是明确哪些材料已齐、哪些会阻断办理、哪些条件仍需确认，并给出可执行的出门前行动卡。

## 加载边界

在以下条件同时满足时使用：

- 用户正在为一次明确的线下或线上生活事务做准备；
- 用户提供了通知、指南、预约说明或机构要求中的至少一种；
- 用户希望核对材料、条件、有效期、截止时间或办理前置事项。

以下请求不调用本 Skill：普通旅游攻略、通用生活建议、法律责任判断、医疗诊断、投资决策、紧急灾害处置，以及没有任何来源材料的“凭经验告诉我要带什么”。来源缺失时，只能输出所需输入清单，不能生成确定性材料要求。

## 输入门禁

1. **登记来源**：为每份通知、网页正文、截图转写和材料清单分配 `S1`、`S2` 等编号，记录文件名、来源日期和当前性。
2. **确认任务对象**：至少取得事务名称、办理日期或参考日期、办理方式，以及会改变条件的必要身份类别。只收集“本人/代办、成年人/未成年人”等最小信息，不要求证件号码。
3. **检查可读性**：列出 OCR 失败、截断、缺页、表格错位和无法访问的链接。关键段落不可读时，整体结果至少为 `needs_confirmation`。
4. **处理当前性**：用户提供的通知记为 `user_provided_current`；已在本次运行核验的官方来源记为 `officially_verified`；无法确认时记为 `unknown`；来源已明确过期时记为 `stale`。没有当前官方核验时，不宣称规则仍为最新。

## 标准工作流

### 1. 先提取要求，再查看现有材料

逐条建立要求表，避免根据用户已经拥有的材料反推通知要求。每项保留：

- 原文材料或动作名称；
- `required`、`conditional` 或 `optional`；
- 条件性要求的完整触发条件；
- 文件名、页码/段落/行号和短证据摘录；
- 有效期、份数、原件/复印件/电子版、签字、照片规格等限定。

通知没有写出的“常见材料”不得加入必带清单。确有帮助的常识建议必须放入“非来源建议”，与正式要求分开。

### 2. 解析条件，不替用户猜身份

先判断条件是否 `applies`、`not_applicable` 或 `unknown`：

- 用户信息明确满足条件：`applies`；
- 用户信息明确排除条件：`not_applicable`；
- 信息不足、定义含糊或来源冲突：`unknown`。

条件为 `unknown` 时，状态必须是 `needs_confirmation`。不得为了给出简洁结论而选择更“稳妥”的材料并混入必带清单。

### 3. 对照材料清单

规范化同义名称用于匹配，同时保留来源原文。逐项判定：

- `ready`：材料满足格式、有效期、签字、份数和载体要求；
- `missing`：未提供或明确缺少原件/副本；
- `expired`：按办理参考日期计算已超出明确有效期；
- `conflict`：用户材料与来源字段不一致，或多个来源要求互相冲突；
- `needs_confirmation`：条件或证据不足；
- `not_applicable`：条件明确不适用。

日期计算须展示基准日期和计算依据。相对日期、工作日或“近期”等词语在定义不足时保留原文并标记待确认。

### 4. 计算整体状态

- 存在 `missing`、`expired` 或 `conflict`：`not_ready`；
- 没有阻断项但存在 `needs_confirmation`：`needs_confirmation`；
- 其余适用要求均为 `ready`：`ready`。

现场审核权、机构自由裁量或来源当前性未知时，在限制说明中明确写出，不承诺最终受理结果。

### 5. 生成双层输出

人读版按以下顺序输出：

1. 一句话整体结论；
2. 阻断项及最短补救动作；
3. 待确认条件与最多 5 个澄清问题；
4. 已齐全与不适用项；
5. 按时间和依赖排序的出门前清单；
6. 来源索引、当前性与限制说明。

同时按 [references/output-contracts.md](references/output-contracts.md) 生成机器可读 JSON。用户未要求保存文件时，可在回答中提供紧凑表格；涉及多项要求时，优先保存 `.md` 和 `.json` 两个产物。

### 6. 运行质量门禁

生成 JSON 后运行：

```bash
python scripts/validate_readiness.py readiness.json --strict
```

出现错误时修复来源、条件、状态或整体结论后再交付。无法修复的内容降级为 `needs_confirmation`，并说明缺失输入。不得删除难以处理的要求来通过校验。

## 异常与隐私

- 多份通知冲突：并列展示两侧来源，不自行选定正确版本。
- OCR 或文件读取失败：列出具体页码/文件，继续处理可读部分并降低结论确定性。
- 用户只给材料、未给通知：输出“请补充当前通知或官方指南”，不凭常识判定齐全。
- 用户上传敏感证件：结果只保留材料类型、有效期状态和末尾必要掩码；不复述完整证件号码、住址或健康信息。
- 本 Skill 全程只读，不预约、不提交、不支付，也不代替机构审核。

## 交付前检查

- [ ] 每项正式要求都有来源锚点。
- [ ] 每项条件性要求都有条件和适用状态。
- [ ] 没有新增来源中不存在的必带材料。
- [ ] 日期、原件/复印件、签字、份数和照片规格均已核对。
- [ ] 整体状态与逐项状态一致。
- [ ] 不确定项和非来源建议已单独分层。
- [ ] 敏感信息已最小化。
- [ ] 严格校验为 0 错误、0 警告。
